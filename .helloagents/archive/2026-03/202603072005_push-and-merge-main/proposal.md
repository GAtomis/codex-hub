## 1. 需求

### 背景
当前本地分支 `feat-项目迭代v2-20260307` 已包含完整项目文件与最新本地提交，但尚未推送到远程。用户希望把该分支推送到远程仓库，并进一步将其内容合并到 `main`，使主线同步到最新状态。

### 目标
- 将 `feat-项目迭代v2-20260307` 推送到远程并建立上游关系。
- 将该分支合并到本地 `main`。
- 将合并后的 `main` 推送到远程 `origin/main`。

### 约束条件
```yaml
时间约束: 本轮直接完成分支推送、合并与远程同步。
性能约束: 无特殊要求。
兼容性约束: 保持现有远程仓库与 SSH 配置，不重写历史。
业务约束: 在合并前先校验 `origin/main` 与本地 `main` 的一致性；默认使用非快进合并，保留合并痕迹。
```

### 验收标准
- [ ] 远程存在 `origin/feat-项目迭代v2-20260307` 并指向当前最新提交。
- [ ] 本地 `main` 已合并 `feat-项目迭代v2-20260307`。
- [ ] 远程 `origin/main` 已同步到合并后的最新提交。

---

## 2. 方案

### 技术方案
先抓取远程引用并确认 `main` 没有偏离，再推送功能分支。随后切换回 `main`，使用非快进合并将功能分支纳入主线，并将更新后的 `main` 推送到远程。最后通过分支关系与提交历史校验结果。

### 影响范围
```yaml
涉及模块:
  - 本地分支: `feat-项目迭代v2-20260307`、`main`
  - 远程分支: `origin/feat-项目迭代v2-20260307`、`origin/main`
  - Git 历史: 新增一条 main 合并提交（如需要）
预计变更文件: Git 引用与提交历史，无工作树源码改动
```

### 风险评估
| 风险 | 等级 | 应对 |
|------|------|------|
| 远程 `main` 已被他处更新 | 中 | 先 `fetch` 并校验分支关系，若有分叉则停止盲推。 |
| 合并冲突 | 中 | 在本地合并时立即停止，保留现场并回报冲突文件。 |
| 远程推送失败 | 中 | 保留本地合并结果，输出失败原因并等待后续处理。 |

## 3. 核心场景

### 场景: 将迭代分支正式并入主线
**模块**: Git 分支发布管理
**条件**: 功能分支本地提交已完成，远程可通过 SSH 访问。
**行为**: 推送功能分支、校验远程主线、合并到本地 `main` 并推送主线。
**结果**: 远程和本地主线都包含本次迭代成果，功能分支保留独立历史。

## 4. 技术决策

### push-and-merge-main#D001: 使用非快进合并保留集成记录
**日期**: 2026-03-07
**状态**: ✅采纳
**背景**: 本次需要把功能分支正式并入 `main`，同时保留本次集成行为的可追溯性。
**选项分析**:
| 选项 | 优点 | 缺点 |
|------|------|------|
| A: 快进合并 | 历史简洁 | 不保留明确的主线集成节点 |
| B: 非快进合并 | 保留分支集成痕迹，主线历史更清晰 | 会多一条合并提交 |
**决策**: 选择方案 B。
**理由**: 这是一次从功能分支进入主线的显式发布动作，保留合并提交更利于后续查看主线演进。
**影响**: `main` 将新增一条合并提交，远程主线历史同步增加。
